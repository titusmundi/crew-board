1. What a Crew Board is

A Crew Board is one private web page with everything a small trades business needs to run its live jobs today:

TabWhat it does
ScheduleA Monday to Friday calendar, plus a weekend column, with every task as a coloured bar showing who is on it. A Today card. Alerts when someone is booked twice or a past task was never ticked off. A "By project" list view.
MaterialsPer job, what must be on site by which date, with two ticks: Ordered and Received. Items turn amber when due within ten days and red when late.
ToolsEvery van load in date order, grouped by site, with the main task that day and a tick for "on site".

The owner uses it alone, from a phone or a laptop: drag a task to another day, add a one-off job, mark things done, tick materials, undo a mistake. The page saves itself. Claude handles anything structural, such as a new job, a new colour, a chain of moves or a holiday change.

The key idea: the board is the record for dates, and the vault is the record for reasons. When a date moves, the board shows it. Why it moved, and what was decided, lives in a note Claude keeps current.

2. The starting point: a vault Claude can work in

The board did not start as a board. It started as a notes vault, opened in Obsidian, that Claude Code reads and writes. If you already use a vault like this, you have everything the board needs. If you do not, the free Second Brain starter is one way to set one up, but the Crew Board is a separate, optional add-on and does not require it. In short:

  • Two spaces. A personal space (Thinking/) that only the owner writes in, and a working space (Doing/) that Claude maintains: frameworks, examples, a knowledge base, projects.
  • A rules file one level above the vault (CLAUDE.md), so Claude reads the conventions at the start of every session without being told.
  • A Map (Doing/Map.md) that says what lives where. Everything is reachable from it.
  • An update rule: write things down as they happen. Decisions go, dated, into the relevant note's Decisions log. Surprises go into Gotchas, ideas not acted on go into a Parking lot, and every person mentioned gets a short note.
  • Working style: the owner talks in plain English. Claude writes the notes, explains in small steps, confirms between them, and verifies before calling anything done.

That last rule matters most. The board is only trustworthy because the vault around it stays current.

3. How the board came to life, step by step

Step 1. Capture the jobs in the vault (late August)

The first live jobs went into the vault as project notes: a client note, then a task list with a schedule table (task, who, days, depends on, dates), a materials table and a tools list. Claude built the first schedule from the client's quote: the trades, the order of the work, and a draft sequence of stages.

It worked, but only on a laptop, and only for reading. You cannot drag a task in a markdown table, and a checkbox in a note does not tell you, on site, what still needs ordering.

Step 2. Decide: a published page, not a note (31 August)

Decision: build the board as a published page rather than an Obsidian note, because markdown cannot do colour-coded views or working checkboxes. Recorded, dated, in the board's own vault note on the day it was made.

Claude generated a single self-contained web page from the vault's schedule, materials and tool lists, and published it as a private Claude artifact with a stable link. One colour per job. The job names at the top double as filters.

Step 3. Make it the daily tool (early September)

The owner started opening the board every morning. Two habits came out of that week: a short command (/board) that prints the link, and a bookmark and shortcut file so it is never more than one tap away. Claude rebuilt the board from the vault whenever the plan changed.

Step 4. The silent failure (version 2)

Ticks for materials and tools were added, saved through a separate data file. It looked as if it worked. It did not: no data file was ever published, so every tick lived only in the browser where it was made. It went unnoticed for a while, because each device showed its own ticks back.

Lesson: a save that "seems to work" must be proven. Tick something, reload, open it on another device. Only then is it done.

Step 5. Hand the board to the owner (version 3, 15 September)

The owner was asking Claude to move tasks several times a day. Version 3 let the owner do it alone:

  • Drag a task to another day (press and hold on a phone). The whole task moves and keeps its length, skipping weekends and closed days.
  • Open a day to mark a task done, move it to a date, or delete it (tap twice). Add a one-off task. Undo anything for a few seconds.
  • Double-bookings flagged in red, except deliberate half-day handovers.
  • The page saves itself by republishing a full copy of itself with the new data inside, a few seconds after a change.

The first self-save came back intact that evening and carried about 100 old ticks from browser storage onto the board. From that day the board, not the vault, was the record for dates.

Decision: moving a task moves only that task. The tasks carry no dependency data, and a silent chain reaction would surprise more often than it would help. Pushing a chain stays a request to Claude, who lists the moves and confirms first.

Step 6. A category for small jobs (15 September)

Half-day and two-day jobs did not fit as "projects". A fifth category, Small jobs, was added in its own colour: each small job is a task under it, with the client and area in the task's note. It has materials and tools lists and a card showing the next one up, but no finish date, because the category never finishes.

Step 7. Teach the calendar the truth (October)

The board started with the full public holiday list closed, the cautious default. A demolition booked on a public holiday showed as "closed" on the board, though the crew was working. When asked, the owner said: we work every day except the week between Christmas and New Year. The calendar rule was rewritten in the vault, every date was checked against its real weekday, and the board's closed days were changed to match.

Step 8. Read the board back before touching it (October)

Two finished jobs still showed open tasks, because the owner had stopped ticking things off once the work was done. Claude read the live board first, confirmed with the owner, marked only those two jobs' tasks and materials done, checked that every other job was untouched, and republished. The local backup copy was refreshed to match.

Step 9. Feed the rest of the business

Because the vault holds the real durations, lead times and working days, everything else draws on the same facts: the written schedule each client receives before work starts, the daily updates, the website brief, quotes. The board is one view of a system, not a separate app.

4. The rules that made it reliable

For Claude

  1. Read the live board before changing it. The owner edits it directly, so the published page is the record. Take the data from the live page, apply the change to that, republish to the same link.
  2. Never republish from an older local copy. Every move and tick since that copy would be lost.
  3. Change only what was asked. Then diff before publishing: only the intended lines may differ.
  4. Keep the three blocks and their ids. The page has one style block (css), one data block (seed) and one code block (app), and it rebuilds itself from them when it saves. Never add a block.
  5. Prove a save before calling it done: change, reload, check on another device.
  6. Never invent a date. Missing facts go on the vault's open questions list and get asked.
  7. Check every calendar date against its weekday before writing it.
  8. Write it down the same day: dated Decisions, Gotchas and Parking lot in the board's vault note.
  9. No street addresses, full client names or prices on the board. Neighbourhood and first name only.

For the owner

  1. The board is where dates live. Move things there yourself.
  2. Ask Claude for structure: a new job, a new colour, a chain of moves, holidays, realigning material dates after a big move.
  3. Tick things off as they happen, including the last tasks of a finished job. An untidy board stops being trusted.
  4. If the status says "Changes on this device only", press Save now.

5. Build your own

What you need

  • An Obsidian vault with a Doing/-style working space and a Map, opened by Claude Code at the folder above it.
  • Claude Code with a paid Claude plan (Pro, Max, Team or Enterprise). The free claude.ai plan does not include Claude Code.
  • The ability to publish a private Claude artifact from Claude Code, so the board can be shared with only you and can save itself. The setup tests this before it says it is done.
  • The Crew Board (this plugin). Obsidian is free, and the kit adds no other cost.

Install the kit

In a terminal, with the Claude Code command-line tool installed, run these two commands:

claude plugin marketplace add titusmundi/crew-board
claude plugin install crew-board@crew-board

Restart Claude Code if it asks. To keep the files yourself instead, download or clone the repository and use the path to the folder in the first command. Install steps change, so check code.claude.com/docs/en/plugins if anything here does not match what you see.

Run it

  1. Open Claude Code at your vault's parent folder and say: "Set up my Crew Board." The crew-board-setup skill takes over.
  2. Answer its questions one at a time: who works on your jobs, which jobs are live, the tasks and days for each, your working days and closed days, and the critical materials and tools.
  3. It builds the page from the template, publishes it privately, and tests that a save round-trips before saying it is done.
  4. It writes Crew Board.md and Working days and holidays.md into your vault and links them from your Map.
  5. Type /board any time to get the link.

Your first week

  • Open the board every morning. Move tasks yourself as the day changes.
  • Each time something surprises you, tell Claude, and it goes in Gotchas.
  • At the end of the week, ask Claude to read the board back and update the vault's project notes.
  • Keep the local master copy (Tools/crew-board.html) as your backup. The live board belongs to your Claude account.

6. How it keeps evolving

The board went through three versions and several smaller changes in six weeks. None were planned in advance. Each came from using it. What made that safe:

  • Every change starts as a sentence from the owner ("we work holidays", "I need small jobs too") and ends as a dated Decision in the board's note. Six months later, the reason is still there.
  • Versions, not tweaks. A big change (like making tasks editable) is built as a new version, with the previous one kept as a backup file until the new one has proven itself in daily use.
  • The vault answers questions the board raises. When the board showed a closed day the crew was working, the fix was a rule in the vault first, the board second.
  • Read back regularly. Ask Claude to read the live board into the vault: what finished, what slipped, what is still open. That keeps both sides honest.
  • Parking lot, not scope creep. Ideas that are not needed today are written down and left alone.

A good monthly check (10 minutes): Are finished jobs ticked off? Do closed days match reality? Are there tasks dated in the past? Is anything in Gotchas worth fixing now? Is anything in the Parking lot now needed?

7. Lessons and gotchas

What happenedWhat to do
Ticks saved only in one browser for days, unnoticed.Prove every save on a second device.
Material needed-by dates did not follow a dragged task.After a big move, ask Claude to realign them, and review the list first.
Every save reloads the page.Normal. The tab and scroll position come back.
Two devices edited at once, and the later save won.Edit from one device at a time.
Holidays were closed by default but the crew worked them.Ask about working days on day one, and write the answer down.
A finished job still showed open tasks for weeks.Tick the last tasks the day the job ends.
A local copy fell behind the live board.Always read the live board before any change, then refresh the local copy after.
